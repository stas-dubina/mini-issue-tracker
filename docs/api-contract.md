# Mini Issue Tracker — API-контракт

Дев’ять маршрутів для FR-01–FR-07 і технічних перевірок. Правила полів, [часткового оновлення](requirements.md#часткове-оновлення) та [переходів](requirements.md#життєвий-цикл-заявки) визначені у вимогах.

## Формати відповідей

Тіла запитів, що змінюють дані, та відповіді мають формат JSON. Успішні запити повертають об’єкт або масив. Позначення в таблиці маршрутів наведено нижче.

```json
{"id":7,"title":"Помилка входу","description":"","status":"OPEN","priority":"medium","assignee_id":null,"created_at":"2026-11-23T10:00:00Z"}
```

Це приклад **Issue**. Поле `assignee_id` може містити `null`.

```json
{"id":41,"issue_id":7,"author_id":1,"text":"Помилку відтворено","created_at":"2026-11-23T10:15:00Z"}
```

Це приклад **Comment**.

```json
{"id":1,"name":"Agent A"}
```

Це приклад **User**.

## Коди й формат помилок

Помилка містить `error.code` та `error.message`. Для `422` додається `error.field` з адресою помилкового поля або частини запиту, наприклад `body.title`, `query.status`, `path.id` чи `body`. Текст повідомлення описує першу виявлену помилку. Клієнт може орієнтуватися на машинний код.

| HTTP | Код | Умова |
|---|---|---|
| 200 | — | Успішна перевірка доступності, читання або зміна, включно з повторним встановленням поточного статусу. |
| 201 | — | Створено заявку або коментар. |
| 404 | `issue_not_found` | Заявки із зазначеним ID немає; формат ID коректний. |
| 409 | `state_conflict` | Валідне редагування закритої заявки або валідний цільовий статус, заборонений матрицею переходів. |
| 422 | `validation_error` | Некоректний ID, фільтр, тип чи значення поля, відсутнє обов’язкове поле, відсутнє або некоректне JSON-тіло чи недозволена властивість тіла; невідомий або повторений параметр запиту. |

Порядок перевірок наведено в [каталозі результатів](requirements.md#каталог-результатів). Параметр маршруту `id` — додатне ціле число. Некоректний `id` дає `422`. Якщо формат `id` коректний, але відповідної заявки немає, повертається `404`. У запитах з JSON-тілом дозволені лише поля, вказані для маршруту. Невідомі й повторені параметри запиту дають `422` на всіх маршрутах за DEC-06. Навіть однакові повторені значення відхиляються. У списку заявок явне порожнє значення фільтра дає `422`, відсутність фільтра вимикає відповідне обмеження.

## Маршрути

Стовпець «Вхід» охоплює параметри шляху, параметри запиту й тіло. Успішні відповіді використовують формати, описані вище. Параметри запиту дозволені лише в GET /issues. Тіло запиту передбачено лише для POST і PATCH. GET-запити надсилаються без тіла; його вміст, якщо переданий, не використовується для фільтрації чи інших операцій. Типи полів, null і межі задає контракт даних; ID і час у прикладах ілюстративні, а не отримані від запущеного сервісу.

| Метод і шлях | Вхід | Успіх | Помилки |
|---|---|---|---|
| `GET /health` | Шлях без параметрів; параметри запиту й тіло не потрібні | `200`, об’єкт `{"status":"ok"}` | `422` для недозволених параметрів запиту |
| `GET /users` | Шлях без параметрів; параметри запиту й тіло не потрібні | `200`, масив User у порядку ID | `422` для недозволених параметрів запиту |
| `POST /issues` | Тіло: обов’язковий `title`, необов’язкові `description`, `priority` | `201`, Issue | `422` для некоректного тіла або параметрів запиту |
| `GET /issues` | Параметри запиту: необов’язкові `status`, `priority` | `200`, масив Issue. Для обох фільтрів діє AND | `422` для некоректного, невідомого чи повтореного параметра запиту |
| `GET /issues/{id}` | Шлях: `id` | `200`, Issue | `422` для некоректного ID або параметрів запиту, `404` для відсутньої заявки |
| `PATCH /issues/{id}` | Шлях: `id`. Тіло: одне або кілька з `title`, `description`, `priority`, `assignee_id` | `200`, заявка з оновленими даними (Issue) | `422` для некоректного ID, тіла або параметрів запиту, `404` для відсутньої заявки, `409` для закритої |
| `PATCH /issues/{id}/status` | Шлях: `id`. Тіло: обов’язковий `status` | `200`, заявка з поточними даними (Issue) | `422` для некоректного ID, тіла або параметрів запиту, `404` для відсутньої заявки, `409` для забороненого переходу |
| `POST /issues/{id}/comments` | Шлях: `id`. Тіло: обов’язкові `author_id` і `text` | `201`, Comment | `422` для некоректного ID, тіла або параметрів запиту, `404` для відсутньої заявки |
| `GET /issues/{id}/comments` | Шлях: `id` | `200`, масив Comment | `422` для некоректного ID або параметрів запиту, `404` для відсутньої заявки |

## Приклади успішних запитів

У рядках зі зміною заявки або додаванням коментаря тіло запиту наведено після шляху. Приклади використовують один послідовний сценарій.

| Запит | Відповідь |
|---|---|
| `GET /health` | `200 {"status":"ok"}` |
| `GET /users` | `200 [{"id":1,"name":"Agent A"},{"id":2,"name":"Agent B"}]` |
| `POST /issues {"title":"  Помилка входу  "}` | `201 {"id":7,"title":"Помилка входу","description":"","status":"OPEN","priority":"medium","assignee_id":null,"created_at":"2026-11-23T10:00:00Z"}` |
| `GET /issues?status=OPEN&priority=high` | `200 []`, якщо є лише щойно створена заявка з пріоритетом `medium` |
| `GET /issues/7` | `200 {"id":7,"title":"Помилка входу","description":"","status":"OPEN","priority":"medium","assignee_id":null,"created_at":"2026-11-23T10:00:00Z"}` |
| `PATCH /issues/7 {"assignee_id":2,"priority":"high"}` | `200 {"id":7,"title":"Помилка входу","description":"","status":"OPEN","priority":"high","assignee_id":2,"created_at":"2026-11-23T10:00:00Z"}` |
| `PATCH /issues/7/status {"status":"CLOSED"}` | `200 {"id":7,"title":"Помилка входу","description":"","status":"CLOSED","priority":"high","assignee_id":2,"created_at":"2026-11-23T10:00:00Z"}` |
| `POST /issues/7/comments {"author_id":1,"text":"Помилку відтворено"}` | `201 {"id":41,"issue_id":7,"author_id":1,"text":"Помилку відтворено","created_at":"2026-11-23T10:15:00Z"}` |
| `GET /issues/7/comments` | `200 [{"id":41,"issue_id":7,"author_id":1,"text":"Помилку відтворено","created_at":"2026-11-23T10:15:00Z"}]` |

## Приклади помилок

Запити нижче використовують стан після успішного сценарію, де заявка 7 закрита.

| Запит | Відповідь |
|---|---|
| `POST /issues {"title":"  АБ  "}` | `422 {"error":{"code":"validation_error","message":"Назва має містити 3–120 символів після обрізання.","field":"body.title"}}` |
| `PATCH /issues/7 {}` | `422 {"error":{"code":"validation_error","message":"Передайте хоча б одне дозволене поле.","field":"body"}}` |
| `PATCH /issues/7/status {"status":"OPEN"}` | `409 {"error":{"code":"state_conflict","message":"Перехід із CLOSED до OPEN заборонений."}}` |
| `POST /issues/7/comments {"author_id":1,"text":"   "}` | `422 {"error":{"code":"validation_error","message":"Коментар має містити хоча б один непробільний символ.","field":"body.text"}}` |
| `GET /issues/999` за відсутності заявки 999 | `404 {"error":{"code":"issue_not_found","message":"Заявку не знайдено."}}` |
| `GET /issues?status=OPEN&status=CLOSED` | `422 {"error":{"code":"validation_error","message":"Параметр не можна повторювати.","field":"query.status"}}` |
| `GET /issues?sort=id` | `422 {"error":{"code":"validation_error","message":"Невідомий параметр.","field":"query.sort"}}` |
| `GET /issues/0` | `422 {"error":{"code":"validation_error","message":"ID має бути додатним цілим числом.","field":"path.id"}}` |

Для кількох помилок одного рівня клієнт використовує code та field першої поверненої помилки, а не очікує фіксованої черговості полів. Пріоритет різних етапів перевірки незмінний за DEC-05. Наприклад, `{}` для ID 999 дає 422; коректний PATCH для відсутньої заявки з ID 999 — 404; коректний запит на редагування наявної закритої заявки — 409. В усіх трьох випадках дані незмінні.
