# Mini Issue Tracker — вимоги ЛР №1

Основне джерело правил даних і поведінки. Основа — вихідний запит замовника та розділи 2–3 методички ЛР №1. API й майбутні тести посилаються на цей документ.

## Функціональні вимоги

| ID | Вимога |
|---|---|
| FR-01 | Створювати заявку з назвою, описом і пріоритетом за правилами моделі даних. |
| FR-02 | Повертати одну заявку або впорядкований список. Фільтри `status` і `priority` працюють окремо. Якщо передано обидва, застосовується логічне AND. |
| FR-03 | Частково змінювати назву, опис і пріоритет. Статус змінюється окремою операцією. |
| FR-04 | Змінювати статус за матрицею переходів. |
| FR-05 | Призначати одного з двох тестових користувачів виконавцем, змінювати виконавця й знімати призначення. |
| FR-06 | Додавати й переглядати коментарі наявної заявки. Кожний коментар має відомого автора. |
| FR-07 | Зберігати заявки й коментарі в SQLite між перезапусками. Відхиляти некоректні вхідні дані без зміни збережених даних. |
| FR-08 | **ЛР №4.** Пропонувати категорію, пріоритет і короткий підсумок. Отримання рекомендації не змінює заявку автоматично. |

Сервіс локальний, із синтетичними даними. У межах проєкту немає реєстрації, автентифікації, ролей доступу, сповіщень, вкладень, видалення заявок, повнотекстового пошуку, пагінації та обов’язкового графічного інтерфейсу. Довідник користувачів не підтверджує особу.

|---|---|---|

Для помилки поля відповідь називає поле або частину запиту. | Надіслати некоректний `title`, запросити відсутній ID і спробувати заборонений перехід. Перевірити статуси, коди та наявність повідомлень за API-контрактом. |
| NFR-03 | Автоматизовані тести використовують окрему тимчасову базу SQLite. | Запустити тести з окремим шляхом до БД і перевірити, що контрольний запис у локальній робочій БД не змінився. |

## User stories та критерії приймання

### US-01 · FR-01 · Створити заявку

Як учасник команди, я хочу створювати заявки про проблеми, щоб команда могла взяти їх у роботу.

- **AC-01-01.** Створення з назвою «  Помилка входу  » без опису й пріоритету повертає заявку з обрізаною назвою «Помилка входу», описом `""`, статусом `OPEN`, пріоритетом `medium`, згенерованим ID і часом у UTC.
- **AC-01-02.** Назва з двох символів після обрізання відхиляється, і заявка не з’являється у списку.
- **AC-01-03.** Назви з 3 і 120 кодових точок Unicode після обрізання приймаються; назва зі 121 відхиляється з `422` без створення запису.
- **AC-01-04.** Опис `""` і опис із 2000 символів приймаються без зміни тексту; 2001 символ або `null` дають `422` без запису.

### US-02 · FR-02 · Переглянути та відфільтрувати заявки

Як учасник команди, я хочу читати заявки й фільтрувати список, щоб знаходити проблеми, з якими треба працювати.

- **AC-02-01.** Для заявок `OPEN/high`, `OPEN/low` і `CLOSED/high` фільтр `status=OPEN` повертає перші дві, `priority=high` — першу й третю, а обидва фільтри разом — лише `OPEN/high`. Кожний список зберігає порядок створення.
- **AC-02-02.** Валідна комбінація фільтрів без збігів повертає `[]`.
- **AC-02-03.** За наявним ID повертається відповідна заявка. Якщо ID має коректний формат, але заявки з таким ID немає, повертається повідомлення про її відсутність.
- **AC-02-04.** Невідомі чи порожні значення фільтрів, значення з неправильним регістром, невідомі або повторені параметри запиту дають `422`, навіть якщо повторені значення однакові.
- **AC-02-05.** ID `0`, `-1`, `abc`, `1.5` у шляху дають `422`; коректний додатний ID відсутньої заявки дає `404`.
- **AC-02-06.** Якщо дві заявки мають однаковий `created_at`, список повертає їх за зростанням `id`, також після застосування фільтрів.

### US-03 · FR-03 · Відредагувати заявку

Як учасник команди, я хочу змінювати окремі поля заявки, щоб виправляти дані без повторного введення решти.

- **AC-03-01.** Якщо для відкритої заявки передати лише нову назву, змінюється тільки назва.
- **AC-03-02.** Запит із коректною новою назвою й пріоритетом `urgent` відхиляється. Повторне читання показує попередні значення.
- **AC-03-03.** Запит із тілом `{}` до наявної відкритої заявки дає `422`. Заявка залишається без змін (DEC-01).
- **AC-03-04.** Валідна нова назва для закритої заявки відхиляється. Збережена назва залишається попередньою.
- **AC-03-05.** Передавання `null` для опису або поля `status` у загальному PATCH відхиляється. Заявка залишається без змін.
- **AC-03-06.** Невідоме поле, системне поле `id` або `null` для `title` чи `priority` у PATCH дає `422`; попередні дані збережені. Порожній опис `""` дозволений і очищає лише опис.

### US-04 · FR-04 · Змінити статус

Як учасник команди, я хочу оновлювати статус заявки, щоб було видно етап роботи.

- **AC-04-01.** Операція статусу дозволяє `OPEN → IN_PROGRESS`, `OPEN → CLOSED` та `IN_PROGRESS → CLOSED`. Після кожного переходу читання показує цільовий статус.
- **AC-04-02.** Спроба `CLOSED → OPEN` дає `409`. Статус залишається `CLOSED`.
- **AC-04-03.** Повторне встановлення будь-якого поточного статусу успішне. Збережена заявка не змінюється.
- **AC-04-04.** Спроби `IN_PROGRESS → OPEN` і `CLOSED → IN_PROGRESS` дають `409`. У кожному випадку зберігається початковий статус.
- **AC-04-05.** Невідоме значення статусу, `null`, відсутнє поле `status` чи додаткове поле в операції зміни статусу дає `422` без зміни заявки.

### US-05 · FR-05 · Призначити виконавця

Як учасник команди, я хочу призначати або знімати виконавця, щоб бачити відповідального за заявку.

- **AC-05-01.** Для відкритої заявки `assignee_id` зі значенням `1` призначає Agent A, значення `2` призначає Agent B, а `null` знімає призначення.
- **AC-05-02.** Значення `3` відхиляється. Попереднє призначення зберігається.
- **AC-05-03.** Зміна назви без поля `assignee_id` зберігає попереднього виконавця.
- **AC-05-04.** Валідне перепризначення або зняття виконавця закритої заявки дає `409`; виконавець залишається попереднім.

### US-06 · FR-06 · Додати та переглянути коментарі

Як учасник команди, я хочу додавати й читати коментарі, щоб зберігати обговорення разом із заявкою.

- **AC-06-01.** Коментар від відомого автора до наявної заявки, зокрема закритої, з’являється у її списку з текстом, автором і часом. Кілька коментарів показуються в порядку створення.
- **AC-06-02.** Коментар, що містить лише пробільні символи, дає `422`. Список коментарів не змінюється (DEC-02).
- **AC-06-03.** Змістовний текст із 1000 символів зберігається як передано. Текст із 1001 символу відхиляється. Довжина включає крайні пробіли (DEC-02).
- **AC-06-04.** Невідомий автор відхиляється. Для валідного коментаря до відсутньої заявки система повідомляє, що заявку не знайдено.
- **AC-06-05.** GET коментарів наявної заявки без коментарів повертає `200 []`; для відсутньої заявки повертає `404`.
- **AC-06-06.** Коментарі з однаковим `created_at` повертаються за зростанням `id`; текст із крайніми пробілами зберігається дослівно за DEC-02.

### US-07 · FR-07 · Зберегти дані між перезапусками

Як учасник команди, я хочу читати збережені заявки після перезапуску, щоб зберігати результати роботи.

- **AC-07-01.** Після створення заявки, призначення виконавця, зміни статусу й додавання коментаря сервіс перезапускається з тією самою БД. Заявка читається за тим самим ID, її дані й коментар збережені.
- **AC-07-02.** Запит на створення заявки з некоректним пріоритетом `HIGH` відхиляється; після перезапуску новий запис відсутній у списку.
- **AC-07-03.** Після відхиленого PATCH із коректною назвою та некоректним пріоритетом і перезапуску з тією самою БД усі поля мають попередні значення.

### US-08 · FR-08 · Отримати рекомендацію AI (ЛР №4)

Як учасник команди, я хочу отримати запропоновану категорію, пріоритет і підсумок, щоб швидше опрацювати заявку.

- **AC-08-01.** Успішна рекомендація містить категорію, пріоритет і короткий підсумок.
- **AC-08-02.** Якщо рекомендований пріоритет відрізняється від збереженого, після отримання рекомендації заявка зберігає свій попередній пріоритет.

|---|---|---|---|---|---|---|

| Issue.title | string | Клієнт. Обов’язкове при створенні, необов’язкове у PATCH | — | Ні | Обрізати крайні пробільні символи. 3–120 символів після обрізання | У загальному PATCH до закриття |
| Issue.description | string | Клієнт. Необов’язкове при створенні й у PATCH | `""` при створенні | Ні | 0–2000 символів, зберігати як передано | У загальному PATCH до закриття |

| Comment.id | integer | Сервер при створенні | Генерований | Ні | Додатний унікальний ключ | Ні |

| Comment.text | string | Клієнт. Обов’язкове при створенні | — | Ні | Щонайменше один непробільний символ. Максимум 1000 символів початкового тексту. Зберігати текст як передано (DEC-02) | Ні |
| Comment.created_at | datetime | Сервер при створенні | Поточний час UTC | Ні | Представлення в API — дата й час ISO 8601 з `Z` | Ні |
| User.id | integer | Тестовий довідник | `1` або `2` | Ні | Додатний унікальний ключ | Ні |
| User.name | string | Тестовий довідник | `Agent A` для `1`, `Agent B` для `2` | Ні | Фіксоване ім’я для відповідного ID | Ні |

Типи JSON перевіряються без неявного перетворення. Рядок `"1"` і логічне значення `true` не є цілими числами. Довжина рядків рахується в кодових точках Unicode, без додаткової Unicode-нормалізації. Для назви обрізаються крайні пробільні символи Unicode; коментар і опис зберігаються дослівно. У параметрі шляху `id` приймається десятковий запис додатного цілого з цифр 0–9; інші форми відхиляються. Поля, яких немає в контракті конкретної операції, відхиляються. Для списку заявок фільтри використовують ті самі допустимі значення статусу й пріоритету, що й модель даних.

## Життєвий цикл заявки

| Поточний ↓ / цільовий → | OPEN | IN_PROGRESS | CLOSED |
|---|---|---|---|
| OPEN | Успіх без зміни | Дозволено | Дозволено |
| IN_PROGRESS | Заборонено | Успіх без зміни | Дозволено |
| CLOSED | Заборонено | Заборонено | Успіх без зміни |

Для `CLOSED` дозволені перегляд заявки, читання і додавання коментарів та повторне встановлення `CLOSED`. Загальне редагування, включно з перепризначенням або зняттям виконавця, і перехід до іншого статусу відхиляються.

## Часткове оновлення

| Випадок | Результат |
|---|---|
| Дозволене поле відсутнє | Зберегти його попереднє значення. |
| Передано `assignee_id: null` | Зняти призначення, якщо стан заявки дозволяє редагування. |
| Передано `null` для назви, опису чи пріоритету | Помилка валідації. |
| Передано `{}` | Помилка валідації (DEC-01). |
| Передано невідоме або недозволене поле, зокрема `status` | Помилка валідації. |
| Передано разом коректні й некоректні зміни | Відхилити весь запит. Жодна зміна не зберігається. |
| Передано дозволене поле з поточним значенням | Успішно повернути заявку, якщо її стан дозволяє редагування. |
| Для закритої заявки надійшло валідне редагування | Конфлікт із поточним станом. |

Операція оновлення атомарна. Усі передані дані проходять перевірку перед записом, а перевірка поточного стану й запис виконуються як одна транзакційна операція.

## Каталог результатів

| Результат | Правило |
|---|---|
| Створено заявку або коментар | Повернути створений запис із системними полями. |
| Читання або зміна успішні | Повернути запис або список, а після зміни — актуальний запис. |
| Заявки немає | Для коректного запиту повідомити про відсутність заявки. Це поширюється на вкладені маршрути коментарів. |
| Вхідні дані некоректні | Повідомити про помилку валідації без змін у БД. |
| Операція суперечить стану | Повідомити про конфлікт без змін у БД. |
| Валідний фільтр без збігів або наявна заявка без коментарів | Успішно повернути порожній список. |

Порядок перевірок для запиту з кількома проблемами: валідація вхідних даних, пошук заявки, перевірка поточного стану.

## Зв’язки та впорядкування

- Заявка може мати одного виконавця з довідника або бути непризначеною. Один користувач може бути виконавцем багатьох заявок.
- Кожен коментар належить одній заявці й одному відомому автору. Заявка може мати довільну кількість коментарів, включно з нулем.
- Зв’язки забезпечуються зовнішніми ключами SQLite. Списки заявок і коментарів ідуть від раніше створених до пізніших. Для однакового `created_at` додатковий ключ сортування — `id` за зростанням.

## Журнал уточнень

Ми розглянули по дві неоднозначності вихідного запиту для кожного напряму відповідальності. Для кожної визначили ризик, відокремили задане правило від прогалини та сформулювали остаточне рішення.

| Учасник | Неоднозначність вихідного запиту | Потенційний ризик | Рішення замовника або прогалина | Остаточне технічне рішення |

**Додаткові технічні рішення.** Нову заявку створюємо без виконавця, а призначення виконуємо через PATCH. Закриття блокує редагування виконавця разом з іншими полями загального PATCH. Для однакового часу створення використовуємо додаткове сортування за ID. Строгі типи, формат часу та порядок перевірок фіксують поведінку у випадках, для яких у завданні не визначено технічних подробиць.

## Класифікація суттєвих пропозицій і статус рішень

Початкова категорія пропозицій збережена для простежуваності; усі шість рішень є чинними правилами специфікації. Результати виконаного перехресного рев’ю наведено у [звіті](lab-01.md#результати-перевірки-за-напрямами-перехресного-ревю).

Ми перевірили рішення на контрольних випадках. Для DEC-01 зіставили `{}` з коректним PATCH одного поля; для DEC-02 — текст лише з пробілів, змістовний текст із крайніми пробілами та довжини 1000 і 1001 символ. Для DEC-03 перевірили узгодженість створення без виконавця з подальшим призначенням, перепризначенням і зняттям. Для DEC-04 розглянули два записи з однаковим часом та різними ID. Для DEC-05 зіставили некоректне тіло для відсутньої заявки (`422`), коректне тіло для відсутньої заявки (`404`) і коректний запит на зміну закритої заявки (`409`). Для DEC-06 перевірили невідомий параметр, повтор однакового значення й коректну пару фільтрів. Це перевірка контракту, а не виконання запитів до реалізованого сервісу.

SCOPE-01 і CONFLICT-01 стосуються попередньої специфікації інтерфейсу, яка передбачала ролі, чотири статуси та інші пріоритети. Вони пояснюють відхилення від того матеріалу; правила поточної лабораторної визначає завдання ЛР1.

Для всіх дев’яти маршрутів параметри запиту дозволено тільки в GET /issues і тільки status та priority по одному значенню. Невідомі та повторені параметри, зокрема на маршрутах без параметрів запиту, дають `422`. Тіла POST/PATCH мають бути JSON-об’єктами з дозволеними полями. Відсутнє тіло, null, масив чи синтаксично некоректний JSON дають `422`. Системні поля та assignee_id у POST /issues заборонені. Ці правила є частиною DEC-03, DEC-05 і DEC-06.
